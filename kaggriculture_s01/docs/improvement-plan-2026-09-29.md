# Kaggriculture 9月29日改善計画

## 判断の前提

- [提出履歴](submission-results-2026-09-29.md)にあるOMW原版 `56639976` と観測価値版 `56639982` はともに `COMPLETE`、episode error 0。その後、公開強豪の再評価を経て `cha22` `56654513` と `hybrid2965` `56654813` が提出され、現在の最新2件になった。両者も `COMPLETE` である。
- Public ratingはそれぞれ1511.9（79試合）と1493.7（76試合）。相手・試合数が異なる継続評価なので、この18.2点差から観測価値版の劣位は判定しない。
- [9月28日の実行記録](final-sprint-execution-2026-09-28.md)では、net-stock v2は新規32 seedのローカルscreenで改善した一方、Publicでの転移は確認できなかった。直近のPublic敗戦3件は終局在庫0で、同じ商品への売り注文が多数重なった。先売りと市場競合を優先して調べる。ただし3件は無作為標本ではなく、注文の重複だけでは約定損失を示さない。
- 既存のDiscussionでは、Replayの注文数量と実約定数量・約定価格は異なると報告されている。また公開tapeを相手にしたローカル評価は、seat、Shop系列の変化、Replay抽出のずれで歪み得る。これらは検証設計への手掛かりであり、この提出の敗因が確定した証拠ではない。

## 優先順位

### P0: 9月29日 — 市場損失を定量化する

1. CLIで3提出（原版、観測価値版、net-stock v2）のepisodeを再取得し、提出ID、取得時刻、status、Public試合数を固定する。各提出から勝敗、相手、seat、cash差で層化してReplayを選び、直近3敗戦だけへの偏りを減らす。取得不能な層は欠測として記録する。
2. Replayの市場注文を商品・stepごとに照合し、**注文量、実約定量、実売上、平均約定単価**を分けて集計する。開始時quote×注文量を売上と扱わない。ローカルエンジンでReplayを再現する場合は、記録済みcash推移との一致を確認し、一致しないepisodeは診断から外す。
3. net-stockで先売りが発火した試合について、相手の同商品注文、注文順、約定単価、後続の価格、最終cashを原版との対応seedで比較する。敗戦例だけでなく改善例も含め、先売り発火時と非発火時を別集計する。相手方策やShop系列が変わる再実行は因果的な一手差と呼ばない。

**完了条件:** どの商品・時期・相手条件で先売りが悪化し、どこで改善するかを、実約定と最終cashの両方で説明できる。説明できなければ市場パッチを実装しない。

### P1: 9月29日 — 評価panelを校正する

1. 既存のOMW鏡、Peak、Triadに、市場行動の異なる入手済み相手を加える。Public Replay由来の相手は、自己Replayからのaction抽出一致、seat 0/1の対応、Shop系列の維持を確認する。Shop系列維持・変化の結果を分ける。
2. 原版と観測価値版を同一seed・両seatで比較する。既存8-seed smokeでの一致は差がない証明ではない。差が発火する状態の頻度と、強敵別の勝敗・cash差を確認する。
3. net-stock v2の32-seed改善を、異系統相手と未使用seedで再点検する。多数の容易な相手で平均勝率を押し上げず、接戦の相手別結果を採否の中心にする。

### P2: 9月29～30日 — 単独変更を1件だけ試す

P0で再現性のある損失条件が見つかった場合に限り、その条件だけで先売り量を抑える小さな変更を作る。既存の売却ロジック全体を組み替えたり、複数のguardを同時に重ねたりしない。変更前後のaction差と実約定差を保存する。

| Gate | 評価 | 採用条件 |
|---|---|---|
| Smoke | 8新規seed × 両seat | 完走、error 0、発火条件が想定どおり |
| Screen | 32新規seed × 両seat × 強敵panel | 強敵別の退行がなく、paired score改善 |
| Validation | 128未使用seed × 両seat × 強敵panel | seed単位bootstrap 95%区間の下限が0超、主要相手に明確な悪化なし |
| Holdout | 選定後の未使用seed | 改善方向が一致、error 0 |

主指標は `win + 0.5 × draw`。cash差と実約定は診断指標とする。Validationまで通らない変更は、締切が近くても最終2枠へ進めない。

### P3: 9月30日 — 最終提出を固定する

9月30日23:59 UTC（10月1日08:59 JST）の締切より前に、CLIで最終評価規則と最新2件のID・`COMPLETE`・episode errorを再確認する。新候補が全gateを通った場合のみ単一`main.py`にbundleして提出物の内容とSHA-256を照合し、提出後に状態を確認する。通らなければ、すでに提出済みの `cha22` と `hybrid2965` を最新2枠に維持する。未検証の方策で枠を埋めない。

## 判断を変える条件

- Public ratingの短期差だけでは候補を入れ替えない。対戦相手・試合数・評価時刻を添えて推移を見る。
- 終盤在庫の問題は、終局在庫または回収不能量が勝敗を変える複数例が出た場合だけ再優先する。
- Replay再現のcash、seat、Shop系列が検証できない場合、そのデータを改善効果の根拠にしない。

この計画は調査・検証の順序を定めるものであり、新たな提出を実行した記録ではない。
